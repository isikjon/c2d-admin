ТЗ Админка для ИИ-агента и рассылки сообщений
Задачи:
Общие задачи:
1. Разработка Админки
2. Настройка интеграций с админкой
- интеграция ИИ-агента
- интеграция с CRM (Б24) 
- интеграция с АPI агрегатора для рассылки сообщений
- синхронизация и обмен данными между системами
3. Настройка в админке функционала по загрузке реестра клиентов для последующей рассылки смс через API (есть в АPI)
4. Настроить в админке группировку и сегментирование сообщений и рекламных кампаний (есть в АPI)
5. Мониторинг в админке выполнения целей и отслеживания триггеров. Сбор и выгрузка аналитики по рассылкам. (частично есть в АPI)
Back-end:
6. Проектирование архитектуры backend-системы Админки, включая взаимодействие с API агрегатора рассылок (C2D), ИИ-агентом, личным кабинетом/виджетом и CRM Bitrix24.
7. Разработка backend-приложения Админки с поддержкой мультиорганизационной модели (организации, личные кабинеты, пользователи).
8. Реализация системы аутентификации и авторизации пользователей Админки (логин по email, пароль, первичная двухфакторная аутентификация через email, восстановление пароля).
9. Реализация ролевой модели доступа и разграничения прав (Главный администратор, Администратор ЛК, Пользователь ЛК, Саппорт/тестирование).
10. Проектирование и реализация структуры базы данных в соответствии с ТЗ (организации, пользователи, клиенты, реестры, кампании, диалоги, статусы, продукты).
11. Реализация backend-логики управления организациями и личными кабинетами (создание, редактирование, блокировка, управление пользователями и доступами).
12. Реализация интеграции с API агрегатора рассылок (C2D) для отправки сообщений через WhatsApp, Telegram и SMS, а также получения статусов доставки и ответов.
13. Реализация backend-интерфейсов для создания, настройки и управления рекламными кампаниями и рассылками на базе конфигураций, передаваемых в API C2D.
14. Реализация логики загрузки реестров клиентов (json, xls и др.), включая парсинг, валидацию, дедупликацию и сохранение данных в БД.
15. Реализация механизма подстановки переменных из реестров клиентов в шаблоны сообщений рассылок.
16. Реализация логики автоматического тегирования, группировки и сегментирования рекламных кампаний и сообщений (по продуктам, типам триггеров, датам и статусам).
17. Реализация backend-логики автоматических триггерных рассылок (нет ответа, написать позже, незавершённый расчёт, незавершённое целевое действие и др.) в соответствии с правилами, описанными в ТЗ.
18. Реализация логики таймеров и периодов отправки повторных сообщений (учёт лимитов, окон отправки, количества повторов).
19. Реализация интеграции с ИИ-агентом для подключения к диалогам при ответе клиента и передачи управляющих событий.

Боли:
1. Привлечение разработчиков при настройке рассылки.
2. Нет возможности мониторить переходы по ссылкам (в ЛК или виджет). Из-за этого не можем определить успешность рекламной рассылки, рассчитать конверсию по переходам и выполненным целям (расчет в виджете, заявка на консультацию и т.д.)
3. Нет аналитики по количеству прочитанных/непрочитанных сообщений
4. Нет функционала для проведения А/В тестов. Из-за этого не можем определить качество сообщений и их конверсию
5. Долгая загрузка реестра клиентов
6. Проблема с разделением сообщений на отдельные рекламные кампании и группировка.
7. Сложности в настройке триггерных цепочек 
Краткое описание:
Задача - разработать админку, интегрировать в нее ИИ-агента (уже разработан) и API агрегатора, настроить корректную работу всего функционала на базе Админки.
Интерфейс админки еще в разработке, верстка будет по готовому макету.
API агрегатора включает в себя функционал по рассылке смс в разных мессенджерах, выводит аналитику по рассылкам и рекламным кампаниям, загружает контакты клиентов и т.д.
Рассылка сообщений по клиентам будет происходить в основном через вотсапп, ТГ и смс-сообщения через телеоператоров на базе Админки.
Сообщения будут отправляться в соответствии с реестром клиентов. В реестре будет отображаться контактный номер телефона, имя клиента и доп информация по необходимости (вид банка/СК, номер полиса и т.д.). Переменные из реестра необходимо подгружать в текстовые сообщения. Основная фильтрация и группировка сообщений будет происходить по видам продуктов и рекламных акций.
Под каждый продукт или рекламную компанию, будет готовиться набор триггерных сообщений, прогревов и рассылок, которые будут настраиваться на базе Админки.
В Админке также необходим функционал настройки рекламной кампании и проведения А/В-тестов. Каждый вид сообщений будет в нескольких вариантах для А/В тестов. После рассылки необходимо собирать аналитику по количеству отправленных, прочитанных, заблокированных сообщений и так далее.

4. Логика автоматических рассылок и настройка шаблонов
1. Автоматические триггеры для рассылок настраиваются сразу после заполнения основных полей при настройке рекламной кампании на отдельной странице.
2. Шаблоны необходимы для автоматизированной настройки ответов с последующим подключением ИИ-агента, а также передачи статусов в БД админки и заявки в CRM-систему.
3. Список статусов (триггеров) для авторассылок:
1) Статус “Нет ответа в течении ..х дней/ х часов/ х минут”
2) Статус “Написать позже + (…(дата), …. (время))”
3) Статус “Не закончил расчет”
4) Статус “Не предоставил данные” 
5) Статус “Незаконченное целевое действие” 
4. Для каждого из статусов на странице есть поле, в которое необходимо вписать текстовый шаблон для авторассылки, пример:
Заглавие: Статус “Нет ответа”
Заполненное поле (текст шаблона): “Уважаемый … (имя), напоминаем, что ваш полис заканчивается через 15 дней. Не забудьте продлить полис по ссылке”.
4.3) Заглавие: Статус: “Не закончил расчет”
Заполненное поле (текст шаблона): “ … (имя), ….”
4.5) Заглавие: Статус: “Незаконченное целевое действие” 
Заполненное поле (текст шаблона): “ … (имя), ….”
5. Use case функционала автоматических рассылок:
5.1. Статус “Нет ответа”
1. Админка анализирует список диалогов, определяет диалоги, в которых ответ отсутствовал более установленного времени (по умолчанию 25 часов)
2. При получении статуса диалога об отсутствии ответа в установленное время (25 часов по умолчанию), админка берет заранее сформированный шаблон (п.4.1. раздел - “Логика автоматических рассылок”) и отправляет клиенту сообщение в чат, повторно инициируя диалог: 
“Уважаемый … (имя), напоминаем, что ваш полис заканчивается через 15 дней. Не забудьте продлить полис по ссылке”.
3. Количество повторных отправок сообщений без ответа, устанавливается при настройке рассылки.
4. Если клиент все равно не ответил, а лимит инициированных безответных сообщений достигнут, то админка формирует новый статус для диалога - “Нет ответа после повторных рассылок”
5. При ответе клиента, админка подключает ИИ-агента, который отправляет в БД новые статусы. Исходя из новых статусов настраивается новая логика рассылки или отправляется заявка в CRM-систему
5.2. Статус “Написать позже”
1. Во время диалога, клиент может попросить связаться с ним в другое время. ИИ-агент уточняет точную дату и время для повторного диалога
2. ИИ-агент формирует статус диалога - “Написать позже”, отправляет статус, дату и время связи в админку
3. Админка устанавливает таймер на повторную отправку сообщения (шаблон из п.4.2., раздел - “Логика автоматических рассылок”). Таймер равен дате и времени, которую прислал ИИ-агент + 3 минуты
4. В установленное время, админка отправляет в чат с клиентом шаблон сообщения: “Добрый день, …. (имя). Вы просили связаться с вами …(дата), …. время. Вам удобно сейчас разговаривать?”
5. После отправки сообщения, админка начинает анализировать чат по стандартной логике
6. Если клиент все равно не ответил, а лимит инициированных безответных сообщений достигнут, то админка формирует новый статус для диалога - “Нет ответа после повторных рассылок”
7. При ответе клиента, админка подключает ИИ-агента, который отправляет в БД новые статусы. Исходя из новых статусов настраивается новая логика рассылки или отправляется заявка в CRM-систему
5.3. Статус “Не закончил расчет”
1) После запуска рассылки, на стороне ЛК система отслеживает переход клиента. 
2) ЛК по API передает в Админку статус расчета после перехода по ссылке: 
* Успешный расчет + вид продукта + сумма расчета
* Ошибка расчета (сбой по любой технической причине) + причина ошибки (логирование)
* Расчет не завершен (цель не выполнена: юзер не закончил расчет и не получил итоговую стоимость)
3) На стороне Админки после получения статуса (успешный расчет/ ошибка расчета/ расчет не завершен), в БД диалогов и базе клиентов проставляются статусы по каждому клиенту 
4) На базе статусов в БД (ошибка расчета/ расчет не завершен), формируется список пользователей, кто подпадает под повторную рассылку
-  Учитывается поле “Количество повторных рассылок при невыполнении цели”, определяется какой раз клиенту отправляется сообщение повторно
- Подбирается “Текст рассылки № х”
- Устанавливается “Таймер отправки повторного сообщения при триггере” 
- Устанавливается “Период рассылки”
5) Для клиентов из реестра со статусом “Расчет не завершен” и “Ошибка расчета”, Админка формирует новую рассылку с текстом:
“Вы не завершили расчет стоимости полиса …(название продукта). Хотите рассчитаем полис за вас и предоставим итоговую стоимость? Для вас еще будет действовать скидка 5%”
6) После отправки сообщения, админка начинает анализировать чат по стандартной логике
7) Если клиент все равно не ответил, а лимит инициированных безответных сообщений достигнут, то админка формирует новый статус для диалога - “Нет ответа после повторных рассылок”
8) При ответе клиента, админка подключает ИИ-агента, который отправляет в БД новые статусы. Исходя из новых статусов настраивается новая логика рассылки или отправляется заявка в CRM-систему.

11. Авторизация:

2) При создании новой организации в БД вносится соответствующая запись. При выборе организации предоставляется список из уже существующих в БД
3) Поля для создания кабинета:
1. Название организации
2. ФИО пользователя 
3. Телефон (необязательное)
4. Е-мейл
5. Пароль
6. Роль пользователя
7. Страна
8. Город
4) После сохранения данных, кабинету и пользователю присваивается ID и запись со всей информацией заносится в БД

4.1. Главный админ может просматривать список всех пользователей. В данном списке можно проваливаться в подробную информацию пользователя, а также менять пароли доступа.
4.2. Вкладка “Пользователи” состоит из Таблицы со списком всех пользователей. Список переменных в таблице:
- ФИО пользователя
- Организация
- Город
- Е-мейл
- ID
- Статус доступа
- Кол-во пользователей в организации

- Фамилия

- Страна

- Профиль

- Изменить пароль

- Фамилия
- Имя

- Организация

- Кол-во пользователей в организации
